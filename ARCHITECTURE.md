## I. Overview

**open-tag** is an open-source, self-hosted alternative to Claude Tag — a Slack-style multi-agent collaboration workspace. Humans and AI agents work as teammates in channels, threads, and DMs. Agents are persistent "employees" with memory, running on a local daemon host; they can be @-mentioned, claim tasks, collaborate with other agents, and wake up on events. Data stays entirely within your own network.

> **Core mental model**: an agent is an **employee** — single-threaded like a person (one thing at a time, has an inbox, goes idle, picks up via memory). **Scale out by adding more agents, not by making one agent multi-threaded.** Collaboration happens via messages (channels / DM / tasks). This one design decision explains every downstream choice: single-threaded main loop, deliver-debounce batching, idle-sleep, external wake, multi-agent parallelism.

Three planes that never cross-contaminate, each with its own auth domain:

```
Human/Web plane    React SPA  → REST /api/*       (Bearer JWT + header x-server-id), socket.io real-time
Control plane      Server ↔ Daemon: WS /daemon/connect?key=  (always the backbone; S→D commands / D→S status)
Agent data plane   Agent process → HTTP /agent-api/*  (Bearer per-agent token sk_agent_* + header x-agent-id), agent uses `open-tag` CLI
```

**Agent lifecycle**: `start → active →(idle timeout) sleep (kill process) → start again (with archived sessionId) → resume`.
- **No separate wake operation**: wake = server re-sends `agent:start` with the saved `sessionId`; the runtime resumes via `--resume` (claude), `thread/resume` (codex), `--session-id` (copilot, idempotent create-or-resume), `--session` (opencode, captured `ses_…` id), `-r` (kimi, captured `session_…` id), `--session` (pi, captured UUID), or `--resume` (cursor, captured UUID).
- **Idle-sleep is implemented** in daemon `agentManager.ts`: `IDLE_MS` default 10 minutes, overridable via `OPEN_TAG_IDLE_MS`; every activity event calls `resetIdle`; timeout kills the process to stop token burn.
- cwd = `~/.open-tag/agents/<agentId>/` (persistent workspace + `MEMORY.md`; after compaction the agent re-reads `MEMORY.md` to reconstruct context).
- **Status is two-dimensional** (daemon `agentManager` emits; `ws.ts` writes `agents.status/activity` to DB):
  - `status` = lifecycle: `active | sleeping | inactive`
  - `activity` = current state: `online | working | thinking | sleeping | offline | error`
  - Running: `active / working·thinking·online`
  - Idle-sleeping: `sleeping / sleeping` (idle timeout or process exit; @-mention triggers auto-resume via `--resume`)
  - Stopped / never started: `inactive / offline` (explicit stop or just created)
  - Machine offline → its agents offline: a machine **confirmed down** (`status=offline` **and** stale `lastHeartbeat`) cannot host a live agent, so the heartbeat sweeper (`machineLiveness.ts reconcileOfflineMachineAgents`) forces every still-live agent on it to `inactive / offline`; a clean daemon WS close does the same immediately (`markMachineAgentsOffline`). `sessionId` is kept so the next wake still `--resumes`; the stale-heartbeat gate keeps a brief WS blip from being mistaken for a dead host, and an agent idle-`sleeping` on a *live* host stays `sleeping`. `machines.status` itself is reconciled three ways so it never lies: WS connect/close (guarded against a stale socket close), a boot pass flipping all machines offline before listening, and the heartbeat sweeper — all in `machineLiveness.ts`.
  - Crashed: `sleeping / error` (non-zero exit code; shown in red in UI but still resumable)
  - Key distinction: `sleeping` (can be @-woken) ≠ `offline/inactive` (needs manual intervention). Frontend `Members.tsx statusOf()` unifies sidebar / overview / Roster rendering; CSS `.dot.*` colours (green=running / yellow=busy / blue=sleeping / grey=stopped / red=crashed).

## II. Codemap (what each file/directory does)

### Control plane + data plane (`src/server/`, TypeScript — the production implementation)

- `index.ts` — HTTP entry point: route order `/agent-api` → `/api` → `/docs/` (`docs-site/dist`, with `/_astro/*` asset support) → static `web/dist` (SPA fallback only for known client routes from `staticRoutes.ts`, so scanner/file paths 404 instead of getting the app shell); mounts socket.io (human real-time), bare WebSocket (daemon control plane), reminder scheduler, and the durable Conversation Turn scheduler. `/docs` redirects to `/docs/`, so self-hosted installs get in-app docs at their own origin while the marketing site points to `https://docs.getopentag.com/`.
- `routes-api/` — **Human-side REST `/api/*`** (directory: a thin `index.ts` orchestrator runs the three auth gates [public → +userId → +serverId], builds a per-gate `ctx` [`ctx.ts`], and dispatches to per-domain handlers — `auth`/`servers`/`agents`/`channels`/`messages`/`tasks`/`reminders`/`attachments`, shared helpers in `shared.ts`; **gate order + gate-2 dispatch order are security-load-bearing** — see header comment in `index.ts`). Groups: auth (dev-login / register / login / join-link `invite-info` + `accept-invite`), servers (create workspace + avatar + member profiles + role management [not self, preserve last owner] + join-links CRUD + machines — incl. offline-row key `reconnect` rotation and rename, both `manageMachines`), notification-settings / sidebar-order, agents (CRUD + start/stop/reset + workspace-files + activity-log + scopes + skills/personality write/delete; lifecycle endpoints wait for `agent-control-ack-v1` and 503 on daemon failure), channels (inbox/unread/saved/threads/dm/files), `GET /mentions` (message-grained @-of-me stream, read or unread, paged), messages (`GET messages/channel/:id` keyset-paginated via `before=<seq>` + `hasMore` / sync / search / `GET messages/:id` single-message, channel-read-gated, declared after sync+search so the bare-id route never shadows them), tasks, `actions/:id/mark-executed`, attachments, reminders, announcements. **Machine RPC endpoints in `servers.ts`** first pin `machineId` to the active tenant; `runtime-models/:runtime` probes dynamic models (~60s cache). The project browser (`GET …/project-directories` returns only shared roots; `POST …/project-directories/query` carries paths in the JSON body so reverse-proxy URL logs never capture them) requires both `manageAgents` and `manageMachines`, targets one `project-browser-v1` daemon connection, and schema-clamps its metadata-only response.
- `routes-agent.ts` — **Agent data plane `/agent-api/*`**: full agent operation surface — message (check/**decide**/send/react/read/resolve), server/info (public + agent-joined channels — `dm`/`thread` types always excluded so internal thread-xxxx names never pollute agent context — plus agents + humans with `description`), channel (join/members/leave), task (list/claim/**assign**/update/new/unclaim), thread (reply/read/unfollow), search, attachment (upload/view — view resolves full uuids *and* 6+-hex short-id prefixes, mirroring `resolveMessageId`), profile (show/update), reminder (schedule/list/cancel/snooze), `action/prepare` (B-mode quick-commit card, scope `action:prepare`; variants channel:create / agent:create). Turn semantics at this surface: `message check` hides collecting/ready/dispatching Turn members and records each `(message, agent)` observation independently; ambient rows stay readable for relevance judgment while addressed `direct|dm|assigned` rows stay hidden until this recipient has `deliveryAdmittedAt`; `message decide`, trigger-bound `message send`, and legacy thread reply enforce the same recipient admission fence before reserving publication; the send-time freshness check reuses the admission/cursor classifier but never consumes the formal observation or advances `lastReadSeq` past unadmitted work. A daemon without `delivery-admission-v2` receives no stable Turn and a fail-loud warning. For a coordinated Task, only the active primary coordinator may claim/assign/update the parent; directed contributors publish scoped results in the Task thread. Human-only `agent_activity_receipt` rows are excluded from agent check/read/thread-read queries and never advance the collaboration loop. **Showcase** is a **front-end static page** (`web/src/views/Showcase.tsx` + `web/src/showcaseData.ts`, assets under `web/public/showcase/`) — no showcase channel, no prop agents, no backend special-cases.
- `conversationTurnPolicy.ts` / `conversationTurns.ts` / `conversationTurnDispatch.ts` / `conversationTurnRecovery.ts` — **Conversation Turn admission, dispatch, and version-gated recovery**: bursts partition by concrete `(server, channel/thread/DM, sender type, sender id)` — one sender never extends another's window, an agent never joins a human Turn. Ambient / same-sender DM messages use trailing settle windows capped by a first-message max wait; agent DM replies merge only within the same reply root and causal depth; explicit mentions are boundaries; task/action/system boundaries dispatch immediately. A collecting Turn reserves responsibility but cannot be checked or answered; dispatch atomically activates the Turn + grants before any wake, picks one sticky/least-loaded owner for human ambient work, capability-preflights every explicit recipient, then fans them out concurrently. `dispatchAttempts` fences activate/renew/finish/retry; partial directed NACKs keep the Turn and explicit grants active. A capable reconnect re-schedules capability-paused and delivery-blocked Turns (unbound recovery requires exactly one capable daemon). Agent-authored ambient wakeups stay suppressed; agent-to-agent DMs are directed causal edges with same-parent retry reuse and repeated-pair dedupe.
- `replyCoordinationPolicy.ts` / `replyCoordination.ts` — **Reply side-effect authority**: the pure policy validates structured intent (`ownership/better_fit/handoff/correction/blocker/new_evidence/unique_expertise`) and decides primary/supplemental eligibility; the DB-backed module assigns the first explicit mention primary and every later explicit mention an independent directed grant, records observation/decisions, privately transfers/releases primary ownership, derives the canonical publication target (task thread vs source channel), waits through the bounded reply-settlement window (`OPEN_TAG_REPLY_SETTLE_MS`, default 5000 ms), reserves publication, and links the consumed grant to the reply. Partial unique indexes enforce one primary + one supplemental; `(replyToMessageId, senderId)` makes all grant kinds one-shot per agent. Confirmed delivery failure releases unconsumed grants; message visibility is never removed to suppress replies.
- `core.ts` — **Message core**: seq allocation, `@mention` parsing (stored structurally in `message_mentions`), persistence, human-side broadcast, Turn attachment, target resolution, and task lifecycle mutations (`convert` / `claim` / `assign` / `unclaim` / `status`). Human- and agent-authored explicit work mentions may Slack-style auto-join reachable non-members; the reach pool still prevents private/DM outsiders. `assignTask()` reassigns an existing task to another agent, records the handoff in the task thread, ensures the new assignee is a thread member, and creates an immediate assigned Turn boundary. Agent delivery and responsibility selection live in `conversationTurnDispatch.ts`; all message persistence still converges here.
- `agentConfig.ts` / `agentDeliveryAck.ts` / `agentDeliveryAdmission.ts` — small server boundaries shared by live dispatch/reconnect: normalize runtime config; own the deterministic delivery waiter; and validate/commit the two-phase recipient admission. `agent:deliver:pending` only renews transport liveness. `agent:deliver:ready` is checked against the authenticated current machine, tenant, bound agent (or sole-daemon unbound topology), Turn, recipient, and sequence; only after `deliveryAdmittedAt` commits does the server answer `agent:deliver:admitted`. Final ACK must match that committed connection record. NACK/disconnect releases an unpublished in-flight admission; successful delivery ids remain idempotent across daemon replacement.
- `agentActivity.ts` — Shared run-Activity persistence and ownership boundary: normalize/prune activity-log rows, start a stream, claim unassigned rows for a public-message segment, retain an active stream across back-to-back messages, and assign log rows to their durable message/receipt owner. The per-agent log remains capped at 500; message snapshots are the durable chat rendering source.
- `agentStartGuard.ts` — Pure start-gating decision for agent lifecycle/wake paths: distinguishes no daemon online, missing selected machine, selected machine offline, and selected machine missing the requested runtime; unbound agents are allowed through for the legacy broadcast fallback. Kept side-effect-free so runtime/machine eligibility is unit-tested without booting the server stack.
- `auth.ts` — **Two auth stacks**: human JWT (`verifyUser`, scrypt password storage) + agent (`resolveAgent`: Bearer = per-agent token, SHA-256 compared against `agents.agentTokenHash` + header `x-agent-id`; token must belong to that agentId → prevents cross-agent / cross-server impersonation; no master key). ⚠️ Daemon WS `?key=` handshake auth (machine key) is **inline in `ws.ts`**, completely separate from agent credentials.
- `scopes.ts` — Agent permissions: 14 scopes + `agentHasScope` / `effectiveScopes` (null = grant all by default).
- `capabilities.ts` — **Human role permissions** (separate system from scopes: scopes = agent data plane, capabilities = human management rights): 8 capabilities × {owner/admin/member} mapping + `can(role,cap)` / `requireCap(serverId,userId,cap)` / `capabilitiesFor(role)`. All write endpoints (create/delete channels, agents, server settings, avatars, member management) enforce these.
- `realtime.ts` — Global publish entry point `publish()`, maps to named events and fans out to server rooms; seq comes from Redis.
- `socketio.ts` — Human-side real-time (socket.io, `/socket.io/`); `emitMapped` sends `message:new` (full message object) / `message:updated` / `task:created` / `task:updated` / `agent:activity` (workspace status + profile trajectory) / `agent:reply` (channel-scoped Activity preview `start`/`activity`/`done`/`error`, keyed by `streamId`) / `thread:updated` (parent message id + parent channel id + reply count + sender id for self-unread filtering) / `agent:created|deleted` / `machine:status`. **Room model**: content events (message/task/agent Activity preview) fan out to per-channel rooms `channel:<id>` (isolation — private channels never leak); metadata events (agent/machine/thread:updated) fan out to `server:<serverId>`. A socket joins its member-channel rooms at connect, and **view-driven** joins any channel/thread it opens via `join:channel` (the server allows joining a channel the user can read — member / public / thread of a readable channel — and refuses private non-members), so realtime tracks what the user is actually viewing.
- `ws.ts` — **Daemon control plane** (bare WS, `/daemon/connect?key=`). Attaches its frame listener before asynchronous machine-key authentication; `wsFrameGate.ts` queues frames received during authentication and drains them in arrival order. Handles D→S `ready`, admission pending/ready/ACK/NACK, status/activity/session/trajectory/reply, heartbeat, and RPC responses. The ready/admitted handler persists admission before the daemon can notify a runtime and keeps per-connection in-flight records so stale, wrong-machine, or mismatched ACK/NACK frames cannot settle another agent's work. `ready.capabilities` is registered before machine indexing/catch-up; a newly current capable connection resumes paused bound Turns and, when it is the server's sole capable daemon, legacy unbound Turns. `ready.runningAgents` reconciles stale/reported live states without rotating tokens. Contextual Activity frames are persisted and forwarded to the matching channel; done/error finalizes the last segment or receipt. Authentication, heartbeat, reconnect catch-up, stale-connection cleanup, and fatal `4001` handling retain their existing contracts.
- `machineLiveness.ts` — Keeps `machines.status` honest **and** drags down-machine agents offline: `reconcileMachinesOnBoot()` (flip all online→offline before the server listens) + `startMachineSweeper()` (periodic — offlines machines whose `lastHeartbeat` is stale, then calls `reconcileOfflineMachineAgents(cutoff)` to force every still-live agent — `active` **or** `sleeping` — on a confirmed-down machine to `inactive / offline`, `sessionId` kept) + `markMachineAgentsOffline(machineId)` (clean WS close path, immediate offline reconciliation for that machine). Thresholds via `OPEN_TAG_MACHINE_SWEEP_MS` / `OPEN_TAG_MACHINE_STALE_MS`.
- `reconnectCatchup.ts` — **Agent-side reconnect catch-up**, the symmetric counterpart to human reconnect sync. Called from `ws.ts` after live-state reconciliation, machine indexing, and durable Turn recovery. Running agents receive durable work only from the canonical dispatcher, never a second legacy body-free notice; legacy non-Turn backlog may still receive one. Dead processes receive `agent:start`, whose startup nudge may pull already-admitted durable backlog. This separation preserves the v2 commit barrier and prevents reconnect from duplicating recipient selection or runtime input. A per-machine cooldown (`OPEN_TAG_CATCHUP_COOLDOWN_MS`) guards flapping links. Agents with `machineId = null` still have no machine-specific reconnect event.
- `daemonHub.ts` — server→daemon routing plus WS-RPC. It tracks server membership, the current `machineId→ws`, and each ready frame's capabilities. `conversationTurnDeliveryBlockReason` requires a bound agent's current daemon to advertise `delivery-admission-v2`; an unbound agent requires exactly one connected capable daemon. Agent lifecycle RPC requires `agent-control-ack-v1`; project-bound start requires `project-directory-v2`. Machine-targeted RPC waiters bind both the exact destination WebSocket and allowed response types, so a second/stale daemon or mismatched frame cannot settle directory metadata requests. Connection replacement evicts the old socket and its capability state so stale close cannot erase the current gate. Durable Turn work and settled lifecycle controls fail closed on version skew.
- `runtimeModels.ts` — **Dynamic model cache + probe**: `getDynamicModels(machineId, runtime)` — checks an in-memory cache (TTL ~60s, key = `machineId:runtime`), on miss fires a `probe-models` WS-RPC via `requestDaemonByMachine` (`daemonHub`) and awaits the daemon's `models` reply, then sorts with the default model first. `DYNAMIC_RUNTIMES` = `{opencode, cursor, pi, claude, codex}`. Errors / timeouts fall back gracefully (callers use the static `MODELS` table). Cache is intentionally in-process (not Redis) — staleness of 60s is acceptable for model lists; a per-machine-per-runtime TTL means the cache auto-refreshes across runtimes independently.
- `storage.ts` — Pluggable object storage boundary: default local disk, switchable to any S3-compatible backend (MinIO/Garage/OSS, `OPEN_TAG_S3_*`); `storageKey` is driver-agnostic. `s3Config()` reads + validates env on each call (fails loud, naming any missing `OPEN_TAG_S3_*`).
- `attachments.ts` / `reminders.ts` / `util.ts` — busboy streaming upload (≤25MB / 10 files; each per-file save self-catches and drains its stream so a failed `saveObject` surfaces as a rejected upload, never an unhandled rejection that crashes the process) / reminder fire → posts system message `@owner reminder:...` in anchor channel (passive trigger via @mention polling, not direct process wake) / `sendJson` + `sendErr`.
- `ratelimit.ts` — in-memory fixed-window per-IP rate limiting (registration) + `clientIp()`: prefers `X-Real-IP`, falls back to the **first** `X-Forwarded-For` hop, both only under `TRUST_PROXY=true`; socket address otherwise (see AGENTS.md transport flags for the proxy trust model).

### Local daemon (`src/daemon/`)

- `index.ts` — Daemon entry point: connects to server control-plane WS, dispatches `agent:start / stop / sleep / reset / profile / deliver / workspace:list / workspace:read / workspace:write / workspace:delete / skills:list / project:resolve / project:browse / ping / probe-models`. `project:resolve` and every project-bound start use the same `OPEN_TAG_PROJECT_ROOTS` policy (`project-directory-v2`); `project:browse` advertises `project-browser-v1`, returns shared roots/lazy child directories, and runs at most one bounded marker-only discovery at a time. No roots means all project binding fails closed. Turn delivery forwards `turnId`, `turnMessageCount`, `attention`, deterministic `deliveryId`, and sequence. While queued it emits `agent:deliver:pending` heartbeats. At the FIFO head it repeatedly sends `agent:deliver:ready` and waits for server `admitted` before allowing `agentManager` to write the runtime notice/startup nudge; adapter acceptance then produces final ACK, rejection produces NACK. Resource-pressure queueing remains pending. Start/stop/reset operations carrying `requestId` return `rpc:ack/nack` only after the serialized lifecycle operation settles. On `agent:start` it injects the agent's `OPEN_TAG_SERVER_URL` = **the URL this daemon connected with**, overriding the server-reported `config.serverUrl`.
- `connection.ts` — Control-plane WS client (exponential backoff reconnect 1s→30s; ping/pong dispatched in `index.ts`, this class manages reconnection + a server-frame watchdog). Backoff resets **only after the server accepts the connection** (first frame received) — not on raw socket `open`, since a rejected key also briefly opens before the server closes it. After acceptance, every server frame arms a watchdog (`OPEN_TAG_DAEMON_SERVER_STALE_MS`, default 90s); if the daemon stops receiving server frames, it closes the socket so normal reconnect runs instead of leaving a half-open process while the server marks the machine offline. A `4001` close (unknown/removed key) is treated as fatal: jump to the 30s cap + log an actionable "re-issue the connect command" error instead of hammering once a second. Socket creation goes through an injectable factory so the backoff/reject/watchdog state machine is unit-tested (`connection.test.ts`) without a real server.
- `agentManager.ts` / `projectDirectory.ts` / `stateFiles.ts` / `runtimeArtifacts.ts` / `deliveryAdmissionStore.ts` — **Agent lifecycle, directory ownership, and delivery admission**: start / sleep / stop / reset / deliver; two-dimensional status `status(inactive/starting/active/sleeping/queued) × activity(online/working/thinking/sleeping/offline/error)` (see §I state machine); **includes idle-sleep** (`IDLE_MS`); wake = `start()` with archived sessionId; `onSession(sid)` pushes `agent:session` to the server immediately. `stateDir = OPEN_TAG_HOME/agents/<id>` owns memory/personality/notes/generated runtime artifacts and is the only reset/delete target; managed file operations reject symlink parents and atomically replace final files. Optional canonical `projectDir` must remain below a daemon-shared root, is revalidated before start, and becomes runtime cwd (hidden/sensitive descendants and symlink escapes rejected; the allowlist controls web disclosure/binding, not the runtime OS user's filesystem access). A DB `starting` claim makes project-path PATCH and every actual start/wake mutually exclusive; project-bound deletion requires a confirmed daemon stop. **Personality override**: on `start()`/`syncProfile()`, a non-empty `stateDir/personality.md` substitutes for the agent's `description` in the system prompt and MEMORY.md `## Role` (`applyProfileToMemory`). Delivery: legacy non-Turn notices keep the 3s debounce; durable Turns bypass it and execute strict FIFO — only the queue head may pass the server commit barrier and then start an Activity preview/runtime input (a rejected barrier produces neither), cold startup absorbs one head Turn into its wake nudge, and `error` does not advance the queue until the adapter's terminal `online` event. Successful ids persist in the bounded `.delivery-admissions.json` ledger; failed/dequeued/stopped ids release the fence; same-id retries re-commit server admission without repeating runtime work. Per-agent lifecycle controls are serialized; delivery epochs cancel stale async preparation.
- `runtime.ts` — Runtime adapter **interface** (pure types: `Runtime{start()}` / `RuntimeSession{deliver,stop}` / `RuntimeCallbacks` / `StartOpts` [separate `cwd` and `stateDir`, plus `runtimeConfig`] / `TrajectoryEntry`). `RuntimeCallbacks.onInitialTurnAdmission` is an exactly-once boundary: adapters accept only after their initial input is admitted (`turn/start`, stdin write, or argv process spawn), and reject pre-admission failures. `spawnSafe.ts` preserves that boundary on Windows by resolving the real executable through `cwd` / `PATH` / `PATHEXT` before using `cross-spawn`; an unresolved CLI uses native spawn so ENOENT is emitted before any misleading `cmd.exe` spawn event.
- `runtimes.ts` — Runtime **registry** (`REG` / `getRuntime()`) + `detectRuntimes()` probes which runtimes are installed locally (`claude` / `codex` / `copilot` / `kimi` / `opencode` / `pi` / `cursor` via `cursor-agent` / `hermes`). `REG` implements all eight adapters.
- `claudeRuntime.ts` — Claude `-p stream-json` adapter: writes a managed prompt below `stateDir/.runtime/claude/` and passes it via `--append-system-prompt-file`; runtime cwd remains the bound project, so Claude's existing project/global instructions and MCP config still load. Parses `thinking` / `text` / `tool_use` blocks into trajectory entries. Spawn failures such as a missing `claude` binary surface as offline/error activity instead of an unhandled daemon exception, so one misconfigured agent cannot kill the daemon process.
- `codexRuntime.ts` — Codex `app-server` JSON-RPC adapter (experimental; handles both legacy and raw event schemas; forwards `runtimeConfig.reasoningEffort` to thread/turn; auto-approves exec/patch/permissions/elicitation; raw v2 de-noises token deltas, maps completed item / tool_start to text/thinking/tool trajectory entries; spawn failures such as a missing `codex` binary surface as offline activity instead of an unhandled daemon exception).
- `hermesRuntime.ts` — Hermes profile adapter (experimental; **one-shot per turn**). Each wake spawns `hermes chat -q <prompt> -Q --source open-tag`, selects either `default` (no `HERMES_HOME`) or a discovered profile, captures native `session_id:` from stderr for resume, and retries fresh when Hermes reports a missing resumed session. Its final-response bridge binds stdout to the checked trigger; an ambient response first requests a reply grant and stays silent when denied, while a directed active grant can publish normally. Hermes owns provider credentials and profile configuration.
- `copilotRuntime.ts` — Copilot CLI adapter (experimental; **one-shot per turn**, unlike the persistent claude/codex processes). Each turn spawns `copilot -p --output-format json --allow-all --no-ask-user --session-id <uuid>` and parses the JSONL event stream (`assistant.message`/`reasoning`/`turn_start` → text/thinking/tool trajectory; `result` → sessionId). Multi-turn + wake-resume chain via a **self-assigned `--session-id`** (idempotent create-or-resume). OpenTag's managed instruction directory is appended to the official comma-separated `COPILOT_CUSTOM_INSTRUCTIONS_DIRS`; existing directories and project instructions remain intact. Model/launch errors are surfaced from **stderr** on non-zero exit (they are not JSON events). `forwards runtimeConfig.reasoningEffort` via `--effort`. Verified against Copilot CLI 1.0.61.
- `opencodeRuntime.ts` — OpenCode CLI adapter (experimental; **one-shot per turn**, like copilot). Each turn spawns `opencode run --format json --dangerously-skip-permissions --dir <cwd> --agent <open-tag-id> [--model provider/model] [--variant <effort>] [--session <id>] <msg>` and parses the `{type, part}` event stream (`text` → text, `tool_use` → tool, `reasoning` → thinking; every event carries `sessionID`). Multi-turn + wake-resume chain via the captured `ses_…` id passed to `--session`. A uniquely named managed primary agent is merged into existing `OPENCODE_CONFIG_CONTENT`; project `AGENTS.md` remains native and untouched. **Two load-bearing gotchas (verified vs 1.15.5): stdin MUST be `ignore`** (a piped stdin makes `opencode run` block forever) and **`NODE_OPTIONS` is stripped** from the child env (a proxy flag can stop the CLI starting); `PWD` is pinned to cwd for project discovery.
- `kimiRuntime.ts` — Kimi Code adapter (experimental; **one-shot per turn**, like copilot/opencode). Each turn spawns `kimi -p --output-format stream-json [-m <alias>] [-r <session_…>] <msg>` (stdin `ignore`) and parses OpenAI-chat-message lines (`{role:assistant,content}` → text, `{role:assistant,tool_calls}` → tool; `{role:meta,type:session.resume_hint,session_id}` → resume id). Installed Kimi `0.19.2` has no independent system/custom-agent flag, so the OpenTag instruction envelope is repeated on every fresh/resumed turn; project instruction files remain untouched. This is lower priority than a native system prompt. **Auth is config-only**: provider + `default_model` remain in the user's existing `~/.kimi-code/config.toml`.
- `piRuntime.ts` — Pi Coding Agent adapter (experimental; **one-shot per turn**, like copilot/opencode/kimi). Each turn spawns `pi -p --mode json --append-system-prompt <state-file> --session-dir <stateDir> [--model provider/id] [--session <id>] <msg>` from the project cwd (stdin `ignore`) and parses the JSON event stream — a `session` event carries `.id`; `message_end.message.content[]` blocks map `{type:text}` → text and `{type:toolCall,name,arguments}` → tool. Prompt/session artifacts remain in state rather than the project. Provider/model come from Pi's own config (`pi --list-models`). Verified against pi 0.73.1.
- `cursorRuntime.ts` — Cursor Agent adapter (experimental; **one-shot per turn**, like copilot/opencode/kimi/pi). Each turn spawns `cursor-agent -p --output-format stream-json -f --plugin-dir <state-plugin> [--model <m>] [--resume <id>] <msg>` (stdin `ignore`) and parses Cursor's Claude-style stream-json: every event carries `session_id`; tools arrive as separate `tool_call` events (`<kind>ToolCall.args` → tool); the terminal `result` event carries the final text + `is_error`. The state-managed plugin contains an `alwaysApply` rule; existing project rules and instruction files remain untouched. **`NODE_OPTIONS` is stripped** from the child env. Runs on the user's Cursor account (`cursor-agent login`).
- `listModels.ts` — **Dynamic model discovery**: shells out to each runtime's discovery command and parses the result. opencode (`opencode models --verbose`), cursor (`cursor-agent --list-models`), pi (`pi --list-models`) → return a full **model list**; Hermes enumerates `default` + profile directories from `HERMES_PROFILE_DIR` and `~/.hermes/profiles`. claude (`claude --help`, parses `--effort`) and codex (`codex debug models`, parses `supported_reasoning_levels` from JSON) → model catalog stays static but per-model **thinking/reasoning-effort levels** are probed. copilot and kimi are **not supported** (their discovery requires an ACP / JSON-RPC-over-stdio handshake that the daemon's current adapter model doesn't implement). Called by `src/daemon/index.ts` in response to a `probe-models` S→D message.
- `prompt.ts` — Assembles the runtime-agnostic agent system prompt: identity + authoritative project/state paths + **full `open-tag` CLI command reference** + reply coordination (`check → decide → send only when granted`) + message format + task flow (`todo → in_progress → in_review → done`) + etiquette / credential hygiene + startup sequence + absolute state-owned **MEMORY.md re-read & compaction self-rescue**. It explicitly prohibits storing OpenTag identity by mutating project instruction files.
- `workspace.ts` — State-directory file tree / symlink-safe file read / write / delete + personality.md + list skills. The file browser and mutations never switch to a bound project. **Skills are resolved per the agent's runtime** (`skillRootsFor`): global provider dirs plus `~/.agents/skills` remain shared through the real `$HOME`; the project-local root is read from bound `projectDir` when present, manager-only and read-only through OpenTag, otherwise it remains the writable state workspace.
- `resourceBudget.ts` — **System resource sampling + pressure budget** for the memory-pressure system: tracks total/available memory, CPU usage, agent count, and start-queue length; `OPEN_TAG_PRESSURE_MEM_MB` (default 500) is the free-memory threshold below which new agents queue and running agents get capped.
- `resourceLimit.ts` — **Per-platform memory pressure enforcement**. Every agent CLI process spawned via `spawnSafe.ts` is assigned to a Windows Job Object (via `koffi` FFI `kernel32.dll`) or Linux cgroup (v2 or v1) — no per-agent limits are set initially. A pressure monitor in `agentManager.ts` runs every 10s: when free memory drops below `OPEN_TAG_PRESSURE_MEM_MB` (default 500), new agents are queued and each running agent gets a `ProcessMemoryLimit` at `current RSS + ceil(400 / N)` MB via `SetInformationJobObject` + working set trimmed via `SetProcessWorkingSetSizeEx` (Windows) or `memory.max` (Linux). macOS support was removed.
- `openTagBin.ts` — **Generates** the `~/.open-tag/bin/open-tag` wrapper script for daemon PATH injection. Two modes: **repo** (runs `src/cli/index.ts` via local `tsx`) and **bundled** (when a sibling `agent-cli.mjs` is found next to the running daemon — i.e. launched from the `@fancyboi999/open-tag-daemon` npm package — runs that bundle via `node`).

## III. Architecture invariants (violation = bug)

- **Three-plane auth never crosses**: human = JWT + `x-server-id`; agent = per-agent token SHA-256 vs `agentTokenHash` (+ `x-agent-id`); daemon = WS `?key=` handshake (machine key). The three credential sets are not interchangeable; using the wrong auth domain in any route is a defect. **Full access-control model — role/capability + agent scopes, the four invariants (tenant isolation, resource-access checks, channel visibility), and the hardening roadmap — is [`docs/authorization.md`](docs/authorization.md).**
- **Observation does not imply reply permission**: every message exposed by `message check` gets an idempotent `(messageId, agentId)` decision row and `observedAt`, including ambient agent chatter. A public agent reply must name its trigger and atomically reserve that agent's active grant — freshness drafts and the older thread-reply route cannot bypass this. First explicit mention → primary; later explicit mentions → independent directed grants; unmentioned observers compete for at most one evidence-bearing supplemental. A one-to-one DM's active primary is immediately `accepted` (`dm_auto_authorized`) — explicit permission, not an obligation; `no_action` stays valid. Publishing any other active addressed `direct|dm|assigned` grant atomically records an implicit accept; no-action, transfer, and ambient grant requests remain explicit. `(replyToMessageId, senderId)` permits at most one publication per trigger/agent. A suspected typo stays pending as `better_fit` until the primary owner accepts, delegates, or abstains. Task replies are authorized only in `task.threadId`; the active primary coordinator reserves the single parent-task claim while directed contributors publish scoped work without claiming (the standing prompt reserves the one-shot public grant for the completed result or a concrete blocker; the server enforces quantity and target). Primary publication waits through a bounded concurrent-decision window and is rejected while a transfer is pending; confirmed delivery failure releases an unconsumed grant, and silent observers stop blocking after the window.
- **Control-plane WS is always the backbone**: all daemon ↔ server commands and status travel over `/daemon/connect`; none go over HTTP.
- **Seq is globally monotonically increasing and unique** (Redis INCR per server): drives unread tracking (`channel_members.lastReadSeq`), the channel-history keyset cursor (`GET /api/messages/channel/:id?before=<seq>` → older page + `hasMore`, hitting the `(channelId, seq)` index), and offline catch-up endpoint `/api/messages/sync?since=`. Thread replies keep their own thread-channel cursor, but user-facing channel badges aggregate unread thread replies onto the parent channel id; raw thread channel ids are not exposed as top-level sidebar unread keys. **Each source clears independently**: reading the channel advances only the channel-own cursor, opening a thread advances only that thread's cursor — so `POST /api/channels/:id/read` returns `{channelId:<parent>, unread:<remaining aggregated>}` (a thread read rolls onto its parent) and the client renders that exact value rather than blindly zeroing the badge. Self-authored messages do not count as unread, including task lifecycle `system` audit messages because they carry the initiating actor's `senderId`. ⚠️ In the steady-state, human-side real-time uses socket.io with full `message:new` payloads (carries the entire message object); the web client does **not** currently consume the sync endpoint for incremental catch-up.
- **An agent joins a channel "caught up" at the watermark, not from seq 0**: when an agent becomes a `channel_members` row — created → `#all` (`routes-api/agents.ts`), CLI `channel/join` (`routes-agent.ts`), admin add-member / channel-create-with-members (`routes-api/channels.ts`), or `@`-mention auto-join (`core.autoJoinMentioned`) — its `lastReadSeq` is initialized to the channel's current max seq via `core.addChannelMembers` (→ `core.channelMaxSeq`), so the agent's first `message check` surfaces only **post-join** messages instead of the channel's entire pre-join backlog (which it can still pull on demand via `message read`). The one exception is **`@`-mention auto-join**, where the watermark is `triggeringSeq-1` so the `@` that pulled the agent in stays unread (the agent must see it). **Users keep `lastReadSeq=0`** — the human UI intentionally shows channel history as unread on join. This is purely an *initial-value* change: the unread predicate (`seq > lastReadSeq`) and the reconnect catch-up idempotency are unchanged. ⚠️ Thread-membership inserts deliberately stay at `0` (task-assignee → thread, thread auto-follow on reply) so the assignment / system message that triggered the join stays visible.
- **A task always carries a number, scoped to its channel** — `taskStatus IS NOT NULL ⟺ taskNumber IS NOT NULL`. The only two paths that promote a message into a task (`createMessage({asTask})`, `convertMessageToTask`) mint the number; the status mutators (`claimTask` / `unclaimTask` / `setTaskStatus`) all carry an `isNotNull(taskStatus)` guard so they can never turn a plain message into a numberless task. Agent `task/claim`·`task/update` on a non-task message convert it first (canonical mint), so the agent CLI keeps its "grab a message as work" gesture without ever producing a `#null`. **Numbering scope is per-channel-type**: `dm` channels number per-DM (`tasknum:dm:<channelId>` — each 1:1 conversation has its own #1), every other type shares the per-server counter (`tasknum:<serverId>`); `reconcileCounters` advances both scopes to the live DB max on boot. ⚠️ A bare `task #N` is unique only **within its scope** (a DM #1 and a channel #1 coexist) — see tech-debt-tracker.
- **@mentions are stored as structured `message_mentions` rows** and are the single source of truth: the frontend linkifies `@name` from each message's own `mentions[]` (`messageRender.processMessageContent`), so an `@` the server never recorded (e.g. a non-member in a private channel / DM) renders as plain text rather than a fake clickable mention. Two read paths, do not conflate: the **channel-aggregated inbox** (`/api/channels/inbox`) computes `hasMention` only inside `if (unreadCount > 0)`, so it surfaces an `@` only while its channel still has unread — an already-read `@` drops off (by design, it's a triage list). The **Mentions activity stream** (`/api/mentions`, `mentions_target_idx`) is message-grained and read-or-unread — the canonical "who pinged me" history powering the Inbox Mentions tab.
- **A non-empty message body never renders as an empty bubble**: `messageRender` renders markdown but **never raw HTML** (no `rehype-raw` — no arbitrary-HTML/XSS surface). Raw HTML in a body is downgraded to **literal escaped text** (`remarkHtmlAsText`), so an all-HTML message shows its source instead of being silently dropped. Rendering must degrade visibly, never to nothing.
- **Mention auto-join (Slack-style) — a thread inherits its parent channel's @-reach**: `@`-mentioning someone not yet in the channel adds them to `channel_members` before the mention is recorded (`core.autoJoinMentioned`, candidate pool from `core.mentionAutoJoinPool`), so the mention actually delivers (wake / inbox) instead of being silently dropped. The pool = who already has access to the space, so adding them leaks nothing: a **public `channel`** → the whole workspace; a **`thread`** → resolves to its **parent channel** and reuses *its* reach (the same parent-channel inheritance `socketio.canReadChannel` uses for read access — public-parent thread → workspace, private-parent thread → its parent's members only); **`private` / `dm`** (and threads under them) → current members only, so an `@` to a non-member stays a no-op (never pulls in an outsider → no leak).
- **Threads anchor only on real (user/agent) messages**: `resolveTarget` (`core.ts`) creates a thread off the parent message a `#channel:<shortid>` resolves to; a `shortid` that lands on a **system message** ("X created task / claimed / moved …") is rejected (`return null` → `/agent-api` `404 TARGET_FAILED`). System messages have no "open thread" affordance in the UI, so a reply threaded onto one would be delivered + persisted but **unreachable** — the same silent-loss failure mode as an empty bubble.
- **Thread targets must round-trip through `resolveTarget`** — the stable thread identity is the **parent message id prefix**, never the thread *channel* id. The agent plane accepts both `#channel:shortid` (caller-relative, good when the agent can already resolve the parent channel/DM) and `thread:shortid` (stable across public/private/DM and cross-agent handoff). The message header (`fmt` in `routes-agent.ts`) still renders a thread-anchor message as `#chan:<m.id8>` (its own id = the thread's parent), matching `addressableTarget`'s historical convention. Emitting the thread channel id instead made the shown target unresolvable (404), so agents reusing it silently failed to reply into the thread (`test/threadTargetRoundtrip.integration.ts`). Handoff / follow-up paths should prefer `thread:shortid`, because a new assignee may be a member of the thread but not of the parent private channel or original DM.
- **`name` is the @mention handle, validated as a machine-safe identifier on creation** (`^[A-Za-z][A-Za-z0-9_-]*$`, ≤`MAX_AGENT_NAME` (64) chars since the column is unbounded `text`, `core.invalidAgentName`, enforced in `POST /api/agents` + frontend `CreateAgentModal`). It is used verbatim as `@<name>` (`parseMentions`, CLI, web) and as the `dm:@<name>` lookup key, so spaces / punctuation / emoji / leading digits would break mention parsing and DM resolution. Display-friendly text (Chinese, spaces, emoji) belongs in `displayName`, which is unconstrained. `users.name` carries a DB `UNIQUE` constraint; `agents.name` has a **per-server partial unique index** `agents_name_uniq` `(serverId, name) WHERE deleted_at IS NULL` — unique among **live** agents only, so a soft-deleted name frees up for reuse; `POST /api/agents` rejects a duplicate live name with **409** via `ON CONFLICT` against this index (race-proof — no SELECT-then-INSERT gap).
- **`POST /api/agents` requires a valid, same-tenant `machineId`** — the web create modal marks Computer required; the route independently rejects a missing/empty `machineId` with **400** and a `machineId` that doesn't resolve to this server's `machines` row with **404** (existence-hiding, consistent with the repo's other ownership pre-checks). Rebind after creation is still impossible (`PATCH /api/agents/:id` excludes `machineId`), and pre-existing unbound rows rely on the legacy `broadcastToDaemons` fallback — see tech-debt I77.
- **Credential hygiene**: plain-text API keys / tokens only in DMs or private channels, **never in public channels**.
- **`storageKey` is driver-agnostic**: switching local ↔ S3 requires no changes to business logic.
- **Agent communication is unified through the `open-tag` CLI** (generated at `~/.open-tag/bin`, injected into the agent's PATH). Claude agents do **not** use MCP. What the agent cannot see in its context effectively does not exist — knowledge is persisted to the workspace `MEMORY.md`.
- **Agents are single-threaded / one agent = one session (intentional design, not a limitation)**: one agent = one process, one session; durable Turns execute in strict FIFO. While busy, a later Turn remains server-persisted but recipient-invisible, has no Activity preview, and is not written to runtime input until the current adapter returns to terminal `online`. Legacy non-Turn notices may still debounce. **Parallelism lives at the team level (multiple agents collaborating), not inside a single agent** — "employee mental model" (see §I): scale by hiring more people, not by making one person multi-thread. `Task` and sub-agents are **not blocked** (inherited from the host machine's tooling), but the standing prompt does not encourage their use → **do not build logic that depends on which sub-agents happen to be installed, and do not add `/fork`-style intra-agent parallelism**.
- **Single file ≤ 1000 lines** (split if exceeded). The former 1093-line `routes-api.ts` is now the `routes-api/` directory; the largest single file is currently `src/server/core.ts` — check with `wc -l` rather than trusting a written count (recorded numbers here drifted stale twice).

## IV. Boundaries (made explicit because they are easy to miss)

- `/api` (human) ↔ `/agent-api` (agent) ↔ `/daemon` WS (control) — three independent entry points demultiplexed in order in `index.ts`.
- `replyCoordination.ts` is the sole reply-grant state transition boundary; prompts and runtime adapters may request/consume through `/agent-api`, but cannot authorize publication themselves.
- `conversationTurns.ts` is the sole burst-admission/Turn-lifecycle and attempt-fencing boundary; `conversationTurnDispatch.ts` is the sole responsibility-selection and wake-delivery boundary.
- `realtime.publish()` — the **sole fan-out point** for all human-side real-time events.
- `storage.saveObject/readObject` — the **sole boundary** for all object I/O.
- `runtime.ts` interface — all differences between claude / codex / copilot / opencode / kimi / pi / cursor (incl. persistent-process vs one-shot-per-turn lifecycles) are contained behind adapters; the upper-layer `agentManager` is runtime-agnostic.
- Daemon ↔ server protocol (message `type`) — D→S defined in `ws.ts`; S→D defined in `core.ts` / `conversationTurnDispatch.ts` / `daemonHub`. This is the control-plane contract. **Turn delivery fence (`delivery-admission-v2`, daemon 0.13.0+)**: S→D `agent:deliver` carries `{turnId, turnMessageCount, attention, deliveryId, streamId, seq}`. D→S `agent:deliver:pending` renews the waiter without accepting work. At its FIFO head the daemon sends `agent:deliver:ready`; the server validates the authenticated machine/tenant/agent/Turn/recipient/sequence, commits `deliveryAdmittedAt`, then replies S→D `agent:deliver:admitted`. Only then may the daemon inject runtime input. D→S final ACK confirms adapter acceptance; NACK/disconnect releases an unpublished in-flight commit. Retry reuses `deliveryId`; the daemon ledger suppresses repeated runtime work while re-running the server commit handshake after ACK loss/reconnect. **Lifecycle control**: S→D start/stop/reset carries `requestId`; daemon 0.12.0+ advertises `agent-control-ack-v1` and replies `rpc:ack/nack` after the operation settles. **Inline Activity extension**: D→S `agent:reply` carries `{agentId, channelId, streamId, op:start|activity|done|error, entries?}`. `activity` entries are contextual status/thinking/tool events for an ephemeral per-message disclosure; they are never provisional public-message text. A persisted agent message absorbs the current segment, while `done/error` finalizes the last segment or creates a no-message receipt. **Model-discovery extension**: S→D `{type:"probe-models", runtime, requestId}` (sent by `runtimeModels.ts` via `requestDaemonByMachine`); D→S `{type:"models", requestId, runtime, models, error?}` (replied by `listModels.ts` via `index.ts`). Uses the existing `requestId` / pending WS-RPC mechanism. **Version-skew NACK**: for any S→D message carrying a `requestId` whose `type` the daemon doesn't know, the daemon replies D→S `{type:"rpc:nack", requestId, error}` (daemon ≥0.10.1) so the server surfaces "daemon too old" instead of a generic RPC timeout.

## V. Cross-cutting concerns

- `env.ts` must be imported before any module that reads `process.env`.
- `log.ts` spans all three planes; JSONL logs land in `~/.open-tag/logs/`, while console streams are split so platform logs and CLI stdout semantics stay usable.
- `redis.ts` seq / task-number / pub-sub / wake queue are shared infrastructure for real-time and sync.
- `auth.ts` (human/agent) + `ws.ts` (daemon key) + `scopes.ts` (agent permissions) + `capabilities.ts` (human role permissions) are enforced across all routes.
